# 07. 常见问题与故障排查 (FAQ & Troubleshooting)

---

## 1. 客户端为什么要设置 `tls: false`？

客户端直连的是局域网内的网关设备（如 `10.10.10.6:8788`），局域网内不存在对应 Cloudflare 域名的公网 TLS 证书。

真正的 TLS 1.3 / HTTP/2 加密发生在**网关出站连接 Cloudflare 边缘服务器**时，由网关携带真实的后端域名（SNI 与 Host）建立公网握手。若客户端自身开启了 TLS，会在内网阶段就报错证书无效（`certificate expired` 或 `self-signed certificate`）。

---

## 2. 与 Mihomo / Clash 部署在同一主机（OpenWrt）时，在线自动更新失败？

### 原因剖析
在同一台软路由上，为了防止 `edt-gateway` 节点连接死循环，通常会将其设置为“直连放行/绕过代理核心”。而若同机的 Mihomo 运行在 **Fake-IP** 模式下，系统 DNS 被劫持并向网关返回了 `198.18.x.x` 的保留地址。防火墙看到请求来自网关，将其直接放行至物理 WAN 口，导致外网丢弃该不可路由数据包而超时。

### 解决方案
从 **v1.1.10** 起，网关底层已内置 **Anti-FakeIP 穿透 DNS 纯净拨号引擎**：
- 程序自动识别 `198.18.0.0/15` 的 Fake-IP 污染；
- 发生污染时自动穿透直连阿里公共 DNS（`223.5.5.5`）或腾讯 DNSPod（`119.29.29.29`）获取真实公网 IP；
- 同时在 Web 更新控制台支持**自定义加速镜像**与**多渠道容灾探测**，彻底根除该问题。

## 3. 为什么 v2rayN 和 Mihomo 可以共用 8788 端口？

Xray-core (v2rayN) 在明文模式下使用 `HTTP/1.1 POST`，而 Mihomo 在 `tls: false` 时发送 RFC 7540 标准的明文 H2C 前言（`PRI * HTTP/2.0...`）。

网关在 8788 端口通过首包前 24 字节魔数进行毫秒级协议嗅探，分别无损移交至内置的 H2C 或 HTTP/1.1 协议栈，无需为不同客户端分别开设多个端口。

---

## 4. 熔断触发逻辑是怎样的？如何区分物理链路异常与业务阻断？

网关在设计上严格区分网络物理故障与业务层阻断：
- **优选网络故障（不熔断）**：若客户端指定的优选 IP 出现超时（`i/o timeout`）或连接拒绝，属于外部 ISP 物理链路丢包，网关**不计入**后端节点的失败次数，防止因公网波动误将健康的 Worker 域名熔断；
- **业务阻断（计入熔断）**：成功连通 Cloudflare 边缘，但返回 `1101`（脚本崩溃）、`502`、`429`、`521` 时，计入失败次数；
- **阶梯容错**：单节点连续 5 次业务失败后进入 60 秒隔离期，流量自动平滑切至其余节点；60 秒后自动解封试探。

## 5. 控制台“活跃优选服务器 (Prefer Nodes)”卡片为什么不会乱跳动？

从 **v1.0.9** 起，网关实行**规则 A 稳定三级排序**：
1. **默认兜底节点置顶**：配置文件中配置的全局兜底优选服务器始终锁定在第 1 位展示；
2. **请求量降序排列**：按各优选节点的真实处理请求量从大到小依次排序；
3. **节点名称字典序保底**：当请求量相同时按名称字母序排列，彻底消除了刷新和轮询时卡片位置随机乱跳的问题。
