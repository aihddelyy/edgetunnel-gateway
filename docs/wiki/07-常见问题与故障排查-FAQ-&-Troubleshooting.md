# 常见问题与排查

## 1. 客户端为什么要设置 `tls: false`？

客户端直连的是局域网内的网关设备（如 `10.10.10.35`），内网不存在对应域名的公网 TLS 证书。

真正的 TLS 1.3 / HTTP/2 握手发生在**网关出站连接 Cloudflare 边缘服务器**时，由网关携带真实的后端域名（SNI 与 Host）建立公网加密。若客户端自身开启了 TLS，会在内网阶段就报错证书无效（`certificate expired` 或 `self-signed certificate`）。

---

## 2. 为什么 v2rayN 和 Mihomo 可以共用 8788 端口？

Xray-core (v2rayN) 在明文模式下使用 `HTTP/1.1 POST`，而 Mihomo 在 `tls: false` 时发送 RFC 7540 标准的明文 H2C 前言（`PRI * HTTP/2.0...`）。

网关在 8788 端口通过首包前 24 字节嗅探协议类型，分别分发至内置的 H2C 或 HTTP/1.1 解析器，无需为不同客户端开设多个端口。

---

## 3. 熔断触发逻辑是怎样的？

网关区分网络链路层异常与业务层阻断：

- **优选链路故障**：若客户端指定的优选 IP 出现丢包、超时（`ETIMEDOUT`）或连接拒绝（`ECONNREFUSED`），属于物理网络异常，不计入 Worker 业务失败，避免网络波动导致误熔断。
- **业务阻断**：成功连接至 Cloudflare 边缘，但返回 `1101`（脚本崩溃）、`502`、`429`、`521` 时，计入失败次数。
- **熔断隔离**：单节点连续 5 次业务失败后隔离 60 秒，期间流量平滑切换至其余节点；60 秒后自动恢复并重新参与轮询。

---

## 4. Macvlan 容器无法通信或丢包？

通常是宿主机物理网卡未开启**混杂模式 (Promiscuous Mode)**。

Macvlan 会为容器生成虚拟 MAC 地址。部分物理网卡驱动在未开启混杂模式时会直接丢弃非宿主机 MAC 的数据包。

### 解决步骤

1. 临时开启混杂模式：
   ```bash
   sudo ip link set eth0 promisc on
   ```
2. 检查网卡状态（输出应包含 `PROMISC` 标识）：
   ```bash
   ip link show eth0
   ```
3. 在虚拟机（ESXi / PVE）环境下，需在虚拟交换机端口组的安全设置中将“混杂模式”、“MAC 地址更改”与“伪造传输”均设为“接受”。
