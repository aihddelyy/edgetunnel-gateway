# ❓ 常见问题与故障排查 (FAQ & Troubleshooting)

本文档汇总了用户在使用 **EdgeTunnel Gateway** 过程中最常遇到的疑问与典型排障方案。

---

## 🚫 1. 客户端连接与协议问题

### Q1: 客户端配置里为什么必须设置 `tls: false` (或 `security: none`)？
> **答**：客户端连接的是你局域网内的网关设备（如 `10.10.10.35`），内网不存在合法的公网 TLS 证书。真正的端到端 TLS 1.3 / HTTP/2 握手发生在**网关出站连接 Cloudflare 边缘服务器**时，由网关全权负责以真实的 Worker/Pages 域名建立最高强度的加密传输。若在客户端开启了 TLS，会导致客户端在局域网内握手报错（`certificate expired` 或 `self-signed certificate`）。

### Q2: 为什么 v2rayN 和 Mihomo 可以共用 8788 同一个端口？
> **答**：Xray-core (v2rayN) 在 `security: none` 时会将 XHTTP 退化为标准明文 `HTTP/1.1 POST`，而 Mihomo 在 `tls: false` 时会发送符合 RFC 7540 标准的明文 H2C 握手魔数（`PRI * HTTP/2.0...`）。网关在 8788 端口实现了**首包字节嗅探**，在毫秒级内通过纯净 TCP 管道分别分流到专有的 H2C 引擎或 H1 引擎，互不干扰且无协议损耗。

## 🛡️ 2. 节点可用性与熔断机制

### Q3: 经常出现节点熔断，网关的熔断标准是什么？
> **答**：网关实施了严谨的**5 次阶梯容错与故障提纯机制**：
> - **严格区分链路故障与业务阻断**：若客户端携带的优选 IP 网络丢包、TCP 超时（`ETIMEDOUT`）或拒绝连接（`ECONNREFUSED`），属于物理优选链路故障，网关**绝对不扣减 Worker/Pages 节点的可用度**；
> - **真正触发失败的条件**：只有成功抵达 Cloudflare 边缘但明确收到 `1101`（脚本崩溃）、`502`、`429`、`521` 等业务阻断状态码时，才计入 Worker 的真实业务失败；
> - **阶梯容错**：单节点连续遭遇 5 次明确业务阻断后，自动隔离熔断 **60 秒**，期间流量平滑切换至其余健康节点；隔离倒计时结束后自动解封归队。

### Q4: 监控中心显示的节点成功率受优选 IP 影响吗？
> **答**：**不受影响**。经过架构深度“提纯”，物理网络传输层错误（超时、断开、DNS 错误属于优选 IP 链路层）在第一道防线直接拦截，只记录优选节点卡片异常，100% 真实纯净反映 Worker 自身的可用度。

## ☁️ 3. Cloudflare 额度与调度

### Q5: Cloudflare 额度达到多少会自动暂停使用？可以在核心配置里自定义吗？
> **答**：**默认阈值为 95%**。当某个后端关联绑定的 Cloudflare 子账户当日请求额度使用率达到或超过该阈值时，网关在动态调度轮询时会**自动暂停调度该节点（移出健康池）**，优先将流量引流至其他未超限的子账户后端；若全部节点均超过该阈值，网关会自动降级兜底保留所有节点，防止断网。  
> 可以在 Web 控制台的 **【⚙️ 核心配置】** 选项卡中自由调整该设置项（支持 10% ~ 100%，步长 1%）。

### Q6: 为什么监控中心的 Cloudflare 额度会自动联动更新？
> **答**：网关后台运行着每 5 分钟周期的静默巡检任务，全自动轮询 Cloudflare 官方 API 并更新本地缓存。监控中心每 3 秒刷新网关状态时，会自动获取最新额度数据，无需手动进入额度面板即可实时联动呈现。

## 🧠 4. 内存控制与性能调优

### Q7: 为什么控制台核心配置提示 `ℹ️ 标准回收模式 (启动参数可加 --expose-gc)`？
> **答**：这代表当前 Docker 容器的启动命令中尚未注入 `--expose-gc` 参数。
> - 在这种模式下，网关的**首包暂存释放、全链路背压流控、Socket 互锁销毁与深层缓存清理依然 100% 正常工作**；
> - 若想进一步解锁 V8 底层硬核的垃圾回收（释放堆内存碎片），只需在 `docker-compose.yml` 中配置：
>   ```yaml
>   command: ["node", "--expose-gc", "server.mjs"]
>   ```
> - 然后在群晖 Container Manager 中点击**“重新构建/重启容器”**，控制台将变为绿色的 `✅ V8 原生 GC 已就绪`。

## 🌐 5. 容器网络与系统排障

### Q8: 为什么使用 Macvlan 模式分配独立 IP 后，局域网设备无法访问容器或连接时断时续？
> **答**：这是使用 Macvlan 驱动最常见但极容易被忽略的硬性要求——**宿主机物理网卡未开启“混杂模式 (Promiscuous Mode)”**。
>
> - **故障原理**：Macvlan 赋予了容器独立的内网 IP 和**全新的虚拟 MAC 地址**。普通模式下，宿主机物理网卡只接收目标 MAC 为宿主机自己的数据包，看到发往容器虚拟 MAC 的流量会直接在硬件/驱动层丢弃，导致局域网设备无法直连网关容器或大量丢包。
> - **排查与解决步骤**：
>   1. **在宿主机开启混杂模式**：
>      ```bash
>      sudo ip link set eth0 promisc on  # 将 eth0 换成你的主物理通信网卡名称
>      ```
>   2. **检查是否生效**：
>      执行 `ip link show eth0`，若输出的标志中包含 `PROMISC`（例如 `<BROADCAST,MULTICAST,PROMISC,UP,LOWER_UP>`），则说明混杂模式已成功开启。
>   3. **群晖 NAS 开机持久化**：
>      群晖重启后可能重置混杂模式，建议通过【控制面板】➔【任务计划】添加开机 root 触发任务：`ip link set eth0 promisc on`。
>   4. **ESXi / PVE 虚拟机环境**：
>      如果宿主机是虚拟机，必须在外层虚拟交换机（vSwitch）安全策略中，将 **【混杂模式 (Promiscuous Mode)】**、**【MAC 地址更改】** 与 **【伪造传输】** 全部设为 **“接受 (Accept / 允许)”**，否则外层虚拟网卡会直接拦截流量。

### Q9: Docker Macvlan 容器无法直接与群晖 NAS 宿主机互通？
> **答**：这是 **Linux Macvlan 驱动特有的内核安全限制**（宿主机物理网卡无法直接与该网卡上虚拟出来的 Macvlan 容器 IP 直接通信，但内网中其他所有设备如软路由、手机、PC 均可完美通信）。
> - **若你的 Mihomo 运行在内网其他设备（如软路由、独立 PC）**：完全不受影响，直接使用 `10.10.10.35`；
> - **若你的 Mihomo 运行在同一台群晖 NAS 宿主机上**：需在宿主机建立一条通往 Macvlan 的虚拟网桥（在群晖计划任务中开机执行）：
>   ```bash
>   ip link add macvlan-shim link eth0 type macvlan mode bridge
>   ip addr add 10.10.10.200/32 dev macvlan-shim
>   ip link set macvlan-shim up
>   ip route add 10.10.10.35 dev macvlan-shim
>   ```

### Q10: 实时日志流 (SSE) 无法加载或显示空白怎么办？
> **答**：
> 1. 确认没有通过未关闭缓冲的反向代理（如 Nginx / Caddy）访问 8789 端口。若使用了上游 Nginx，请确保配置了：
>    ```nginx
>    proxy_buffering off;
>    proxy_cache off;
>    proxy_set_header Connection '';
>    proxy_http_version 1.1;
>    chunked_transfer_encoding off;
>    ```
> 2. 刷新浏览器页面或检查控制台是否有网络连接断开提示。
